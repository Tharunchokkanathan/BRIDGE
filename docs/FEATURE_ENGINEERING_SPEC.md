## 2. Full 44-Feature Contract

### Categorical Features (4)
1. `station_code`: Fulfillment / delivery hub identifier (e.g. `DBO1`, `DLA3`).
2. `preferred_delivery_method`: Customer default delivery channel (`Front Door`, `Hand to Customer`, `Locker`, `Mailroom`, `Porch`, `Garage`, `Neighbor`).
3. `customer_delivery_preference`: Requested timing (`Morning Only`, `Evening Only`, `Weekday Only`, `Anytime`, `Leave with Guard`).
4. `location_type`: Property physical classification (`Residential`, `Apartment`, `Commercial`, `Locker_Hub`).

### Numerical Features (40)
* **Physical & Routing (11):** `latitude`, `longitude`, `planned_service_time_seconds`, `depth_cm`, `height_cm`, `width_cm`, `package_volume_cm3`, `departure_hour`, `is_weekend`, `month`, `time_window_duration_hours`
* **Customer CRM & Historical Priors (11):** `customer_availability_rate`, `customer_previous_delivery_attempts`, `customer_previous_failed_attempts`, `customer_previous_success_rate`, `address_access_difficulty`, `signature_required`, `historical_zone_failure_rate`, `historical_station_failure_rate`, `seasonal_failure_rate`, `traffic_risk_score`, `weather_risk_score`
* **Engineered Temporal & Volume Signals (12):** `has_time_window`, `window_start_minutes`, `window_end_minutes`, `departure_to_window_start_minutes`, `departure_to_window_end_minutes`, `departure_hour_sin`, `departure_hour_cos`, `day_of_week_sin`, `day_of_week_cos`, `log_package_volume`, `log_planned_service_time`, `preference_departure_mismatch`
* **High-Impact Operational Interaction Features (6):**
  1. `risk_signature_unavailability` $= \text{signature\_required} \times (1.0 - \text{customer\_availability\_rate})$
  2. `risk_preference_departure_clash` $= \text{preference\_departure\_mismatch} \times (1.0 - \text{customer\_availability\_rate})$
  3. `risk_commercial_closed` $= \mathbb{I}(\text{location\_type} == \text{'Commercial'}) \times \mathbb{I}(\text{departure\_hour} \ge 17 \lor \text{is\_weekend} == 1)$
  4. `risk_access_difficulty_heavy_package` $= \text{address\_access\_difficulty} \times \left(\frac{\log(\text{package\_volume} + 1)}{10.0}\right)$
  5. `risk_zone_weather_stress` $= \text{historical\_zone\_failure\_rate} \times (1.0 + \text{weather\_risk\_score})$
  6. `customer_failure_propensity` $= \frac{\text{previous\_fails} + 1.0}{\text{previous\_attempts} + 2.0}$ (Laplace smoothed)

## 3. Real-World Generability for Delivery Partners

Every single input parameter is easily generated by delivery partners:
- **At Order Ingestion:** Scanned dimensions, signature flag, and customer delivery preferences on file.
- **At Route Staging:** Departure hour and geographic zone code.
- **In CRM:** Customer historical track record and rolling availability.

## 4. Live Dynamic Delivery Feedback Loop

When drivers complete a delivery attempt, they submit an update via:
`POST /api/delivery/complete`

```json
{
  "package_id": "PKG-DEMO",
  "outcome": "FAILED",
  "failure_reason": "CUSTOMER_UNAVAILABLE",
  "delivery_notes": "Gate locked, customer not answering intercom"
}
```

### Dynamic Prior Updates:
1. **Customer Track Record Updated:**
   - Increments customer delivery attempts and failures.
   - Recalculates $\text{success\_rate} = 1.0 - \frac{\text{fails}}{\text{attempts}}$.
2. **Bayesian Zone Prior Smoothing:**
   $$\text{Updated Zone Prior} = \frac{\alpha + \text{zone\_failures}}{\alpha + \beta + \text{zone\_attempts}}$$
   *(Using conjugate Beta-Binomial smoothing with $\alpha = 1.8, \beta = 18.2$, prior weight $= 20$)*
3. **Continuous Learning:**
   Subsequent deliveries in that postal zone automatically inherit the updated prior in real time without waiting for batch model retraining.

## 5. Leakage Quarantine Audit

The following fields are strictly quarantined and never enter model matrices:
- `scan_status` (post-dispatch observed outcome)
- `first_attempt_failed` (target variable)
- `route_id` (reserved strictly for route-grouped validation)
- `stop_id`, `package_id` (identifiers)
- `delivery_date`, `departure_time` (raw timestamps)
